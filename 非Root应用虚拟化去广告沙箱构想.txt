非 Root Android 应用虚拟化去广告沙箱构想
=====================================

构想提出：2026-11-02
归档日期：2026-11-03
状态：暂存的第二个独立想法；未立项、未制作原型，也没有完成 Android 15/16 实机验证。
定位：独立于仓库中“统一 APK 开放通用计算基座构想”的另一个研究方向。两者有用户控制执行环境的共同理念，但不要混为同一个项目。

【一、问题与动机】

大量 Android 软件具有广告展示、开屏跳转、跟踪 SDK、过度收集信息、干扰界面等行为。传统去广告方法各有代价：
  · Root + LSPosed/Xposed：控制能力较强，但需要 Root、解锁或其他较高权限，适用范围受设备限制。
  · LSPatch 等重打包方式：无需 Root，但通常需要修改目标 APK 并重新签名，可能破坏官方签名信任关系、影响应用升级、登录、完整性验证和数据保留。
  · DNS/VPN/网络过滤：无需修改 APK，但对应用自身生成的内容、与正常请求混合下发的广告、内部广告 SDK 和界面逻辑控制有限。
  · 无障碍自动关闭广告：不修改目标 APK，但通常是在广告已经出现后再操作，存在延迟、误操作和适配问题。

目标不是获得 Android 系统的最高管理权，也不是在外部已安装应用中强行注入代码，而是让用户主动将原版 APK 放入自己掌控的虚拟执行环境，在该环境内部实行去广告及必要的行为限制。

【二、核心产品：去广告沙箱】

一个普通 Android APK 形式的宿主，即“去广告沙箱”：
  1. 用户导入原版目标 APK（或者在许可范围内选择已安装应用的原版安装文件）。
  2. 宿主通过应用级虚拟化引擎管理虚拟包、虚拟组件、进程、数据目录及必要的 Android Framework API 代理。
  3. 目标 APK 的文件字节和原始签名保持不变，不通过重新打包来植入修改。
  4. 目标应用的代码在容器控制的环境内运行；容器在运行过程中执行网络过滤、系统 API 代理及必要的 Java/native Hook。
  5. 将现有开源去广告项目的相关技术与规则按需移植进宿主，形成由项目自行维护的内置功能。
  6. 为各虚拟应用提供桌面快捷方式，使用户点击原应用图标即可直接进入对应虚拟实例，尽量不需要先打开容器首页。

基本结构：

    Android 15 / Android 16
             │
             └── 去广告沙箱（普通安装的宿主 APK）
                    ├── 应用级虚拟化内核
                    │      ├── 原版 APK 加载与虚拟包管理
                    │      ├── Activity / Service / Intent 代理
                    │      ├── 虚拟文件、数据与环境管理
                    │      └── 进程、通知和兼容层
                    ├── 内置广告过滤与运行时干预
                    │      ├── 网络广告请求过滤
                    │      ├── 通用广告 SDK 处理
                    │      ├── 特定应用的数据与界面规则
                    │      └── 需要时调用 ART Hook 能力
                    └── 用户界面
                           ├── 导入 / 移除虚拟应用
                           ├── 为每个虚拟应用创建桌面入口
                           └── 规则开关、日志、数据与权限控制

【三、明确的技术边界——不要误解成现代 VirtualXposed】

重要约束：
  · 不要求兼容 Xposed/LSPosed 的模块安装格式和 API。
  · 不需要第三方模块管理器、模块作用域管理、通用模块加载生命周期。
  · 我们可以阅读并研究知了、酷安净化、其他应用去广告项目，必要时依照许可证移植其算法、定位方法、过滤规则和实现思路。
  · 仅在确实需要修改目标应用的 Java 方法行为时，集成 LSPlant 等底层 Hook 引擎；不应为了 Xposed 生态兼容而增加复杂度。
  · 优先在容器已有的系统服务代理、文件重定向和网络控制层解决通用问题；针对应用内部广告数据或界面，才使用应用专属 Hook。
  · 功能以“去广告”为中心，可附带阻止过度追踪和不必要的信息读取，但不要把它扩张成全面手机虚拟系统、游戏多开商业 SDK 或通用 Root 模拟平台。

举例：
  网络域名过滤→优先通过网络层处理；
  请求设备标识→优先通过容器的系统 API 代理处理；
  广告 SDK 初始化→可使用有针对性的 Java 方法 Hook；
  App 信息流内嵌广告→按目标 App 版本处理数据构造、解析或显示逻辑。

所有规则应当能够单独开关、回退，避免一条失效规则导致整个 App 无法运行。

【四、保持普通 App 的使用体验】

核心交互目标是“容器退居幕后”：
  · 导入后展示原始名称与图标。
  · 为每个虚拟实例请求创建桌面快捷方式；点击图标直接启动对应虚拟实例。
  · 能支持合理的多任务切换、通知显示与点击返回、分享及打开链接等日常操作。
  · 官方正常安装的同名 App 与沙箱内部实例可以并存，不要求先卸载官方 App。
  · 容器内实例的数据目录独立管理，不假定可以读取外部正常安装 App 的私有数据。

技术提醒：
  · Android 8+ 可通过 ShortcutManager.requestPinShortcut 请求固定桌面图标，通常需要桌面启动器及用户确认，不能保证静默添加。
  · 桌面图标等同于普通 App 的外观，并不意味着 Android PackageManager、系统设置、应用抽屉都认为它是一个真正独立安装的 APK。
  · 最近任务、后台运行、通知、推送、跨 App Intent、Deep Link 与账户登录会比快捷方式困难得多，必须逐项验证。

【五、首要技术目标：找到 Android 15/16 可用的纯应用虚拟化引擎】

不需要支持 Xposed 模块。基础引擎只需无 Root、可运行未修改的原版 APK，并允许宿主控制虚拟环境与适度运行时干预。

已有开源研究候选（以下是截至构想讨论时收集的线索；项目宣传与实际验证必须分开）：

1. NewBlackbox
   https://github.com/ALEX5402/NewBlackbox
   · BlackBox 系分支，含虚拟化引擎源码。
   · 2026 年存在 Android 15/16 网络、WebView 和权限兼容性相关的代码更新。
   · 适合作为优先研究的开源基础候选；“有兼容性修复”不等于“已广泛稳定支持所有 App”。

2. BlackBox Reborn
   https://github.com/fdavids77/BlackBoxReborn
   · 有 Android 16 无 Root 实机测试记录和具体 Android Framework/ART 兼容性修复。
   · 开发日志也详细记录了 WhatsApp 的真实 UID、Play Integrity 等难以解决的问题。
   · 开发规模很小、应用兼容性并不完整；更像研究和补丁来源，而非成熟通用产品。

3. Black's BlackBox
   https://github.com/Black00Z/Blacks-BlackBox
   · 现代 BlackBox 分支，存在 Android 16 相关的启动兼容记录。
   · 需进一步检查实际源码完整性、更新频率、可重复构建和独立测试结果。

4. VirtualApp 开源基础及后续分支
   https://github.com/asLody/VirtualApp
   https://github.com/ServenScorpion/VirtualApp
   · VirtualApp 是历史上成熟且影响很大的应用级虚拟化技术路线。
   · 原始公开代码较旧。商业维护版本声称支持 Android 15/16 乃至更新版本，但最新商业核心代码没有完整公开。
   · 某些分支的 README 近期更新，不代表核心目录的源码同期更新。可借鉴架构与旧功能实现，不能直接假定现代兼容。

5. 其他考察材料
   https://github.com/WaxMoon/MultiApp
   https://github.com/josskixg/renjana
   https://github.com/LSPosed/LSPlant
   · MultiApp 是另一类虚拟容器实现参考，但现代 SDK 开源维护状况需核查。
   · renjana 是较新的 Android 虚拟容器项目，需检验实际完成度。
   · LSPlant 不是虚拟化引擎，只是可选的现代 Android ART Hook 基础组件。

不应仅凭 Stars 数、商业宣传、README 中的 Android 16/17 字样或最近提交时间来判断成熟程度；需要审查核心源码、构建产物、维护记录与真机可重复测试。

【六、如果开源框架不够成熟：开源基础 + 商业样本行为研究】

市场上有商业化、持续适配较新 Android 的应用虚拟化技术及应用。这至少说明相关机制具有工程实践基础，但不代表其实现天然适用于所有设备，也不代表商业 SDK 的最新源码可用。

拟采用的研究方法：
  1. 先将最有希望的开源候选正常编译、安装、运行。
  2. 选取目标测试 APK，在 Android 15/16 真机上复现最具体的失败。
  3. 搜集崩溃日志、Android 组件调度、Binder 调用、ClassLoader、文件路径、系统服务和网络行为。
  4. 在合法授权范围内，把商业产品作为黑盒行为参考，比较同一应用在不同容器中的表现。
  5. 优先通过 AOSP 对应版本源码、公开接口和开源补丁解释兼容性差异。
  6. 必要时针对特定功能分析商业软件样本，再独立编写修复代码；不直接复制未经授权的商业专有代码。
  7. 一次修复一个明确问题，形成可重复测试，逐步积累现代 Android 兼容层。

可以考虑净室式重实现，以功能规格、行为差异和公开资料为依据实现兼容逻辑，尽量控制版权、许可证及代码来源风险。

【七、应主动承认的限制与风险】

1. “不重新签名原版 APK”不代表虚拟运行的身份就等同于官方安装。实际 Linux UID、进程身份、包管理信息及服务器端 Play Integrity 等验证可能仍然识别容器。
2. 非 Root 应用级虚拟化不能赋予容器真实 Root，也不能突破宿主原本的 Linux UID、SELinux 和 Android 权限边界。
3. 容器内部的虚拟应用可能共享宿主真实 UID。虚拟目录隔离需要额外实现和验证；不能宣称获得了内核级、相互独立的安全沙箱。
4. 容器本身会接触虚拟 App 的账户数据、会话和隐私信息，必须把容器视作高信任度软件，审计代码来源、Hook 与网络逻辑，尽量保证本地处理和最小权限。
5. 复杂应用的支付、银行、政务、游戏反作弊、DRM、硬件密钥与高等级完整性验证可能无法兼容；不能把绕过所有检测视为核心验收目标。
6. 由于广告有时与正常内容通过同一 API 返回，通用网络过滤无法覆盖所有广告；应用专属规则会随目标 App 更新而失效。
7. 在普通 APK 宿主下，通知、后台服务、推送、存储、Intent、WebView、原生库和系统版本定制都可能出现兼容性故障。
8. 移植开源去广告项目代码时，应逐一核实许可证、署名和代码复用条件。不能随意混用与项目发布方式不兼容的许可证。
9. 使用商业样本进行测试和逆向研究时应评估当地法律、服务协议及相关授权，优先采用独立实现。

【八、建议的最小验证路线】

阶段 A：纯虚拟化，无任何去广告功能
  · 选出至少一个能编译的候选框架。
  · 在 Android 15 与 Android 16 真机上分别测试导入、启动、退出、重启和多次运行原版 APK。
  · 优先测试几个结构差异明显的普通 App，再测试有代表性的国产常用 App。
  · 验证原版 APK 未改动、无 Root、外部官方 App 未受影响。

阶段 B：最低限度的桌面化体验
  · 为虚拟实例申请桌面快捷方式。
  · 点击图标直接启动实例，并检查最近任务、返回、后台切换。
  · 逐项修复通知及常见分享、跳转流程。

阶段 C：最简单的通用过滤能力
  · 在容器内部增加可关闭、可记录、可回退的网络广告过滤机制。
  · 验证对正常内容、登录、更新的影响。
  · 不以“全应用零广告”为第一阶段目标。

阶段 D：第一个应用专属去广告移植
  · 从许可条件合适、代码相对清晰的现有开源项目中选择一项具体规则。
  · 必要时接入底层 ART Hook，只移植实际需要的调用和处理方式，不实现 Xposed 模块兼容层。
  · 对目标应用的几个版本验证效果、性能与失败回退。

阶段 E：形成可维护体系
  · 通用规则和 App 专属规则分层、独立开关。
  · 记录目标 App 版本、规则来源、失效日志及兼容性矩阵。
  · 所有兼容性修复以真实复现和可重复测试为基础。

最小成功标准：在至少一种 Android 15/16 设备上，以非 Root 宿主运行未重新打包的原版应用；能从独立桌面入口启动；能够启用/关闭至少一项实际有效的容器内去广告规则；关闭规则后仍可正常使用目标应用。

【九、设计取舍与以后再研究的问题】

当前不要急于立项或投入大量开发。后续最需要弄清：
  · 哪一个开源虚拟化核心在 Android 15/16 的可编译性、功能完整性和实机兼容性最好？
  · 国内主要目标 App 的运行问题，是通用 Framework 兼容性问题，还是难以摆脱的实际 UID、完整性检查等系统性限制？
  · 容器内的网络代理与 ART Hook 各自可以在不修改原始 APK 的前提下实现到什么程度？
  · 商业虚拟化样本是否提供了值得复现的明确技术修复，而不只是厂家私有适配？
  · 项目的最小可信安全边界是什么？如何确保容器不会变成新的隐私风险？
  · 以应用去广告为主要用途，维护成本是否会超过它比其他非 Root 方法节省的成本？

一句话总结：
以现有开源 Android 应用虚拟化框架为底座，必要时参考商业样本与 AOSP 补齐 Android 15/16 兼容，在不 Root、不重新打包原版 APK 的前提下，让用户将应用放入自己可控的容器，再把成熟开源项目的广告过滤逻辑按需移植为内置能力；最终提供可从桌面直接启动的“去广告沙箱”。

这是一份构想记录，不代表相关兼容性、隔离安全性或广告过滤效果已经验证。
